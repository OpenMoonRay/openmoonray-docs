26/**
27 * The SceneContext represents all the data for a specific scene in RDL. This
28 * includes all the objects in the scene (SceneObjects) as well as their types
29 * (SceneClasses). It provides some basic functionality for creating
30 * SceneClasses and SceneObjects, iterating through them, finding them by their
31 * unique name, and retreving them so you can query or update their attributes.
32 *
33 * Once the data has been loaded or updated, the rendering libraries should be
34 * given a const reference to the SceneContext. RDL makes heavy use of its const
35 * correct API to indicate which methods and objects are read-only and thread
36 * safe. If you stick to the const API and don't violate its integrity with
37 * any const_casts, it should be completely safe to traverse the SceneContext
38 * and all its objects from multiple threads concurrently.
39 *
40 * Don't worry about calling createSceneClass() or createSceneObject() multiple
41 * times by accident. They both have "create if it does not exist" semantics,
42 * and are effectively no-ops if the class or object exists. In the case of
43 * createSceneObject, it will return the existing object.
44 *
45 * Thread Safety:
46 * - The only points of synchronization in the SceneContext are the SceneClass
47 * and SceneObject hash maps, which are tbb::concurrent_hash_maps. These
48 * control access to the hash map with reader/writer locks, so it should
49 * only be slow in the presence of writers. Even then, it's only slow while
50 * we're inserting the SceneClass or SceneObject into the hash table.
51 * Once the insertion is finished, the lock is released and you can continue
52 * updating the object without holding the lock.
53 * - SceneClasses and SceneObjects do not synchronize access to themselves,
54 * so writing to these objects must only happen in a single thread. They
55 * are completely self contained, though, so you are free to write to
56 * different SceneClasses or SceneObjects in different threads concurrently.
57 */

163 /**
164 * Sets whether or not the SceneContext is in proxy mode.
165 *
166 * When in proxy mode, new SceneClasses will be created such that any
167 * objects of that SceneClass will be proxies, not the actual objects. This
168 * is useful if you want to use RDL to read and write SceneContexts, but
169 * don't want to drag in the dependencies of all the DSOs you're using.
170 * DSOs should never have declare() functions that drag in extra
171 * dependencies.
172 *
173 * Proxy objects can use get() and set() on their attributes as expected,
174 * but you CANNOT safely downcast them to their proxied type. Thus, you
175 * CANNOT use member function interfaces on proxy objects, including the
176 * virtual functions defined by their parent classes. For example, you
177 * CANNOT call createProcedural() on a GeometryProxy object. You can get()
178 * and set() attributes and that's about it.
179 *
180 * It's also important to remember that proxy mode only affects *new*
181 * SceneClasses that are created. Objects created from that SceneClass will
182 * always be created as proxies or not depending on whether the context was
183 * in proxy mode when the SceneClass was created. In general, you probably
184 * want the context to always be in proxy mode or never be in proxy mode.
185 *
186 * @param enabled True to enable proxy mode, false to disable.
187 */
188 finline void setProxyModeEnabled(bool enabled);

203 * SceneClass will be returned. If the class does not exist, the
204 * SceneContext will search the DSO path for a file named the same as the
205 * class name with a ".so" extension and attempt to open it as an RDL DSO.
