6/*
7MOONRAY-XPU START HERE
8
9The current Moonray-XPU implementation offloads the occlusion ray processing to
10the GPU for supported scenes. This is an extension of vectorized mode with some
11special queuing logic to collect occlusion rays for the GPU. Future work will
12extend the GPU processing to regular non-occlusion rays.
13
14XPU is implemented using NVIDIA's Optix 7.0 API, which is built on NVIDIA's
15CUDA SDK.
16
17***** Mode of execution:
18
191) Individual CPU rendering threads queue up occlusion rays via
20 TLState::addOcclusionQueueEntries(). This function then directs rays to the
21 regular vector mode occlusion queue or the XPUOcclusionRayQueue, if available.
222) The XPUOcclusionRayQueue is flushed when full, calling the XPU ray handler.
233) The XPU ray handler calls the GPUAccelerator (via GeometryAccelerator::occludedXPU())
24 to process the batch of rays on the GPU and read the results back from the
25 GPU. It then creates/queues the BundledRadiances for the render buffer.
26
27***** Vector mode fallback:
28
29Not all vector mode features are supported in XPU mode. If the user specifies the
30XPU exec_mode, Moonray will attempt to create the GPU accelerator for the scene.
31If it discovers that the scene requires an unsupported GPU feature, it will
32stop creating the GPU accelerator and fall back to regular vector mode.
33
34***** Source code locations:
35
36Most of the source code is located in this directory. There are additional pieces
37here:
38
39lib/rendering/mcrt_common/ExecutionMode.h:
40 Defines the XPU execution mode enum. Moonray generally treats XPU and vectorized
41 mode the same in most places.
42
43lib/rendering/mcrt_common/ProfileAccumulatorHandles.hh:
44 Defines the XPU execution profiling accumulators, i.e. EXCL_ACCUM_GPU_OCCLUSION
45
46lib/rendering/pbr/core/XPUOcclusionRayQueue.h:
47 Implements a queue for XPU bundled occlusion rays. Future
48 expansion of XPU will add specializations for other ray types.
49
50lib/rendering/pbr/core/PbrTLState.h/.cc/.hh:
51 Holds a pointer to the XPUOcclusionRayQueue so the individual CPU-side threads
52 can submit rays to the GPU. PbrTLState does not *own* the XPUOcclusionRayQueue
53 object - that is owned by the RenderDriver. There is only one XPUOcclusionRayQueue
54 shared by all the threads.
55
56lib/rendering/pbr/handlers/XPURayHandlers.cc/.h:
57 Ray handler functions that are called by the XPUAcceleratorQueue when it flushes
58 rays out of the queue. There are both a CPU and GPU ray handler. The CPU ray
59 handler is invoked if the GPU is busy to avoid blocking CPU threads, which
60 provides automatic load-balancing between the GPU and CPUs. Calls the occludedGPU()
61 function on GeometryAccelerator.
62
63lib/rendering/rndr/RenderDriver.cc:
64 Functions to create/free/flush the XPUAcceleratorQueue that it owns.
65
66lib/rt/GeometryAccelerator.h:
67 Implements occludedGPU() which passes rays to the actual GPUAccelerator (in
68 GeometryManager.) In Moonray, all ray tracing queries go through
69 GeometryAccelerator whether they are scalar/vector/xpu.
70
71lib/rt/GeometryManager.h/.cc:
72 Owns the GPUAccelerator object and creates it in updateGPUAccelerator(), which
73 implements the logic to fall back to regular vector mode if there is a problem
74 creating the GPUAccelerator. Note that GeometryManager creates/updates the
75 regular embree accelerator in finalizeChanges(), but the GPUAccelerator is
76 created at the end of RenderContext::renderPrep() because it needs a fully
77 initialized scene.
78
79***** Error handling:
80
81We need to cleanly fall back to regular vector execution mode if there are any
82problems encountered while setting up the GPUAccelerator. The constructor takes
83a pointer to a std::string that an error message is placed into. If the message is
84empty after construction, no error has occurred and XPU has been successfully
85initialized. Many of the internal API functions use this same pattern, although
86they also return a bool success/fail that is easier to check for than an empty error
87string.
88
89***** Optix data structure zero initialization:
90
91All Optix data structures (structs) are expected to be zero-initialized with "= {};"
92before the members are filled in. This is done in many places in this code.
93NVIDIA's examples do this and it eliminates a potential source of flaky behavior,
94plus the default values tend to be zero so you only need to set the non-defaults.
95
96***** Memory management:
97
98The GPUBuffer class is used everywhere to manage GPU data. You create an GPUBuffer
99object on the host side and it creates/manages a buffer on the GPU. It has methods
100for easily copying to/from the GPU buffer. It will automatically release the GPU
101buffer in its destructor which helps prevent GPU memory leaks.
102
103*/
