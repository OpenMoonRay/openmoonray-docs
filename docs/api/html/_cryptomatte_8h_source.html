19/*
20
21A note on terminology
22---------------------
23
24In the code, we use a mixture of terms derived from the Cryptomatte Specification and Arnold, supplemented by
25our own terms.
26
27We use the following terms of our own:
28
29* fragment: the part of a pixel covered by a surface all having a single id
30
31The Cryptomatte spec (see https://github.com/Psyop/Cryptomatte/blob/master/specification/cryptomatte_specification.pdf)
32uses the following terms:
33
34* ID: the 32-bit id values which correspond to our deep ids
35* coverage: the fraction of a pixel covered by a given fragment
36* layer: a set of 4 output channels (RGBA) containing two ID/coverage data sets
37
38Arnold uses the following terms:
39
40* depth: the number of ID/coverage data sets to be output
41
42The depth is user-specified and defaults to 6. The number of layers output to the EXR file will be (depth + 1) / 2,
43and if an odd depth is requested then the final blue/alpha channel pair will contain zeroes as padding (which compress
44to almost no size in the EXR).
45
46*/

102/* The following notes are adapted from the DeepBuffer mutex description.
103 *
104 * Cryptomatte pixels are independent of each other, so there is no threading hazard
105 * when different threads are writing to different pixels. It is possible
106 * (although uncommon) that multiple threads might write to the same pixel,
107 * so that needs to be protected with a mutex. The simple solution is to
108 * have one mutex per pixel. This would consume a lot of memory, so instead
109 * there is an array of 225 mutexes for the entire image that are shared
110 * between the pixels. Some pixels will share the same mutex, which results
111 * in some extra locking... however testing has shown the overhead is negligible
112 * once there are >= 64 mutexes for ~20 rendering threads. This may need to be
113 * increased as the number of threads increases though.
114 * The mutexes form a 15x15 tile that repeats across the image, and the
115 * getMutexIdx() logic maps a screen coordinate to a [0, 225] tile index.
116 * Note that the tile size is not a multiple of the rendering 8x8 tile size.
117 * This reduces mutex sharing during rendering.
118 */
119 static const int mMutexTileSize = 15;
120 // force mutex to be cache-line aligned for speed
121 struct CACHE_ALIGN AlignedMutex : public tbb::mutex {};
122 AlignedMutex *mPixelMutexes;
123 int getMutexIdx(unsigned x, unsigned y) const {
124 return (y % mMutexTileSize) * mMutexTileSize + (x % mMutexTileSize);
125 }
126};
127
